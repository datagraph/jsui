5.1 What Experience Teaches

There are things you learn from a manual, and then there are things you only learn from sitting down and doing the work. This chapter is an attempt to bridge that gap — to offer you, before you have made the mistakes, some of what you would eventually figure out on your own.

Think of it as advice from someone who has been watching people work with this system for a long time. Not rules. Just habits that tend to serve people well.

5.2 Moving Around Efficiently

  • Use the location bar directly. You can type a URL right into the bar and go there — no need to click through a chain of links. When you know where you are going, go directly.
  • The browser's back and forward buttons work. The application is designed to cooperate with them. Do not be afraid to use the navigation you already know.
  • Open things in multiple tabs. Working on two repositories at once? Keep them in separate tabs. The browser was designed for this.
  • Learn the keyboard shortcuts. A few keystrokes will carry you far:
    • Ctrl+Enter on Windows and Linux, Cmd+Enter on a Mac: Run the current SPARQL query
    • Enter: Submit whatever form you are filling out
    • Escape: Close a dialog when you have changed your mind

5.3 Working Well in the Query Editor

  • Pay attention to the syntax highlighting. The editor colors your SPARQL as you type — keywords one shade, variables another. When something looks wrong, it often is. Trust the visual cues before you trust your memory.
  • Let autocomplete help you. The editor will offer suggestions as you type. Accept them. They reduce the chance of a simple spelling mistake turning into a mysterious error.
  • Keep multiple tabs open. If you are refining a query — trying one variation, then another — use separate tabs for each version. That way you can compare results without losing your work.
  • Choose your format thoughtfully. An HTML table is easy on the eyes. JSON is better if you are feeding results to something else. Pick the format that serves what you are actually doing with the data.
  • When something goes wrong, check the event log. It is quiet, but it sees everything — every run, every save, every error. The answer to what happened is usually in there.

5.4 Taking Care of Your Data

  • Export before you change anything significant. A copy of your data sitting safely elsewhere costs you a few minutes. Losing data you cannot get back costs you much more. This is not pessimism — it is prudence.
  • Test imports with small files first. Before you load thousands of records, load ten. Make sure the format is right, the data looks the way you expect. Then scale up.
  • Use asynchronous import for large datasets. If your file is large, do not make the browser wait for it. The async mode lets the work happen in the background while you carry on.
  • Watch the progress indicators. When an import is running, the system tells you where it stands. Watching that progress bar is not impatience — it is staying informed.
  • After importing, verify with a query. Run a simple SPARQL query against your newly imported data. Make sure it is there. Make sure it looks right. A minute of checking saves hours of wondering.

5.5 Sharing Access Wisely

  • Start people with read access. You can always grant more later. It is much harder to undo the consequences of too much access given too soon.
  • Keep track of who has access to what. Write it down somewhere. People change roles. Projects end. A list you can refer to makes it much easier to keep things tidy over time.
  • Review your collaborator lists from time to time. Access granted for one project does not always need to persist forever. A periodic review keeps things clean.
  • Talk to your collaborators. Tell them what the data is, what they can do with it, and what you would prefer they not do. The system handles permissions, but expectations are set by people.

5.6 Keeping Things Running Smoothly

  • Close tabs you are not using. Every open tab holds state. Dozens of open editors can slow things down. Close what you have finished with.
  • Search and filter rather than scroll. If you have many repositories or views, use the search tools to find what you need. Scrolling through long lists is slower and less accurate.
  • Write efficient queries. An open-ended pattern that could match everything will try to. Be specific about what you are looking for. Your queries will run faster, and the results will be more useful.

5.7 When Things Go Wrong

5.7.1 An Import Did Not Work

It happens. When it does, run through this list:

  • Check that the file format is one the system knows how to read
  • Make sure the file is not too large for the synchronous import path — if it is, switch to async
  • Confirm that you have write permission on the repository you are importing into
  • Look at the event log — it will usually tell you exactly what went wrong

5.7.2 A Query Returned an Error

SPARQL is precise. A small mistake can produce a cryptic error. Try this:

  • Read the SPARQL carefully — look for missing brackets, mismatched braces, undefined prefixes
  • Check that the data you expect to be there actually is there
  • Open the event log and read what it says — the error message is often quite specific about what went wrong
  • Simplify the query. Remove parts of it until it runs, then add them back one at a time. You will find the problem.

5.7.3 Authentication Is Not Working

Before you assume something is broken, check the simple things:

  • Is Caps Lock on? Passwords are case-sensitive.
  • Is the host URL exactly right?
  • Is your network connection alive?
  • If nothing else works, try clearing the browser cache and starting fresh

5.7.4 Collaboration Features Are Behaving Oddly

When something in the sharing or permissions area seems off:

  • Double-check the collaborator's account name — a single character difference makes it a different person
  • Make sure you have the permission to manage collaborators on this repository
  • Confirm you actually clicked Save — changes do not take effect until they are sent to the server
  • Refresh the browser and look again

5.8 Five Things Worth Remembering

  1. Save explicitly. The system does not save for you. When you are done, click Save.
  2. Export before you delete. If a repository or query matters, keep a copy before you remove it.
  3. Test small before going big. Whatever you are about to do with a thousand records, do it first with ten.
  4. The event log knows. When something goes wrong and you are not sure why, the event log usually is.
  5. Give only the access that is needed. You can always add more later. Taking it away is harder.
